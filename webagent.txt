# DeepSeek Web Bridge + GodotAgent — Handoff

Save as: `DEEPSEEK_BRIDGE_HANDOFF.md`

A single document covering what's been built, why each piece exists, the
current state of every file touched, the failure modes we've hit, and
what's still on the table. Written assuming you (the next person reading
this) have the GodotAgent codebase in front of you and no memory of the
conversation that produced this document.

---

## 0. Executive summary

**What this is.** A local bridge that lets GodotAgent — a Godot 4 coding
agent with an OpenAI-shaped LLM client — drive a real, logged-in
`chat.deepseek.com` browser tab as if it were an OpenAI-compatible
endpoint. No Godot-side code changes are required to *speak* to it; the
bridge returns OpenAI-shaped responses, and Godot's existing
`LLMClient.gd` parses them.

**Why it exists.** DeepSeek's free web chat is a large, capable model
that is *not* API-native. There's no `tool_calls` field, no streaming
JSON, no `reasoning_content`. It replies in prose and, if asked, will
inline a JSON object. Godot's `AgentLoop.gd` already had a
synthetic-recovery path for small local models that write tool calls as
text; the bridge repurposes that path for DeepSeek Web.

**What's the actual state.** Working end-to-end on simple tasks.
Recoverable on medium tasks. Fragile on long tasks for three reasons:

1. **The protocol fights the model's training.** DeepSeek wants to
   narrate; we want bare JSON. Every "nudge" and "recovery" we've added
   is a patch for that mismatch.
2. **Every tool call is a whole browser round trip.** 30–90s each.
3. **Message size grows unbounded on context compaction** — the bridge
   used to type the *entire* conversation history into a fresh chat
   every time Godot's `ContextManager` compacted. This is now bounded.

**What was added this round.** Request logging (metrics + raw SSE),
message-size budget with mid-conversation drop, bridge-side tool-result
cap, and a lower `WEB_CHAT` tool-result cap in `ModelProfile.gd`. See
§5 for details.

## 1. Architecture
Godot LLMClient.gd --HTTP POST /v1/chat/completions-->
|
v
bridge.py (FastAPI on 127.0.0.1:5000)
|
| Playwright: type text, press Enter, listen for
| the SSE response the page's own JS triggers
v
chat.deepseek.com (real Chromium, persistent logged-in profile)

Godot AgentLoop.gd <-- OpenAI-shaped JSON <-- bridge.py
text


Key invariants:

- The bridge does **not** reconstruct DeepSeek's internal request shape
  or solve its proof-of-work challenge. It types into the real chat
  input and presses Enter, exactly like a human.
- The bridge does **not** implement tool-calling. It returns DeepSeek's
  plain-text reply verbatim as `choices[0].message.content`.
- `AgentLoop.gd`'s `_extract_fake_tool_call()` recovers tool calls from
  that plain text — the same path small local models already used.

## 3. The DeepSeek web-chat reality

### 3.1 No native tool calling

DeepSeek's web frontend has no function-calling mechanism. The model can
*write* a JSON object if asked, but it's not a first-class tool call the
way OpenAI's `tool_calls` field is. Every tool call arrives as text.

### 3.2 The `THINK` / `RESPONSE` fragment split

Since the "Instant, Expert, Vision — unified and upgraded" UI update,
even Instant mode runs an internal reasoning pass. Captured SSE shows:

```json
"thinking_enabled": true,
"fragments": [{"id": 2, "type": "THINK", "content": "The", ...}]

Then content-append events stream into that THINK fragment. Later, a new
fragment is appended:
json

{"p": "response/fragments", "o": "APPEND",
 "v": [{"id": 3, "type": "RESPONSE", "content": "Hello", ...}]}

Content-append events after this point target the RESPONSE fragment.

Consequence: a naive accumulator that appends every {"v": "..."}
event gets reasoning text mixed into the answer. Fixed in
extract_reply_text by tracking current_fragment_type and only
accumulating when it's exactly "RESPONSE".
3.3 Config endpoints (not chat responses)

DeepSeek exposes several settings/config endpoints. Their JSON looks
like chat responses but isn't:

	/api/v0/users/current/settings/... — per-user settings, including
	model_configs (see §3.4)

	/api/v0/.../search_providers — the search-citation provider list

	/api/v0/.../banner — in-app banner content

None of these go through the bridge. If you're debugging, filter for
chat/completion in DevTools' Network tab.
3.4 The model_configs reality

The user's own account exposes:

    Instant — enabled: true, switchable: true — the only model
    selectable

    Expert — enabled: false, switchable: false — thinking model,
    disabled at the account level

    Vision — enabled: false, switchable: false — image model,
    disabled

think_feature: {} on all three. So there is no user-facing toggle
for DeepThink / reasoning on this account. The reasoning output is a
byproduct of Instant mode's internal pipeline, not something the user
chose. There is no "turn off thinking" button. The parser must filter.
3.5 Search is ON by default

search_state_on_launch: "on" in the user's settings. Search results
are prepended to the model's output as citations. Currently the bridge
does not filter these out. If you see citation garbage mixed into
replies, the fix is another filter in extract_reply_text — but no such
filter exists yet because we haven't captured a search-triggered reply.
4. The tool-call protocol
4.1 What we ask the model for

The bridge prepends TOOL_PROTOCOL_HEADER and the tool schema list to
every fresh-chat prompt. The rule:

    To call a tool, your ENTIRE reply must be one bare JSON object:
    {"name": "<tool_name>", "arguments": { ... }}
    No prose before or after. No code fences. No XML tags.
    One tool call per reply.

4.2 What actually comes back, and how we recover

Three observed failure shapes, each with its own recovery:

Shape A — clean. {"name": "read_file", "arguments": {...}} with
nothing else. _extract_fake_tool_call finds it directly.

Shape B — prose prefix. Let me read that file. {"name": "read_file", "arguments": {...}}. The JSON is intact but there's prose around it.
_find_json_objects still finds the balanced {...}, so recovery works.
AgentLoop adds a specific nudge telling the model that the reply didn't
start with {.

Shape C — truncated prefix. The {"name": opening is missing
entirely. What arrives is "read_file", "arguments": {...}}. This is
the shape produced when DeepSeek's SSE stream splits the tool call
mid-fragment, and it's the one that caused the "it didn't really happen"
episode. Recovery: _recover_truncated_tool_call in AgentLoop, which
scans for a "<identifier>", "arguments": pattern and takes the
identifier as the tool name.

When all three fail: nothing runs, the turn ends as COMPLETED with
no action, and the user sees the agent "stop." This is the worst-case
failure and the reason we log everything now.
4.3 What DeepSeek does NOT do

    Emit multiple tool calls in one reply reliably. It can, but the
    recovery path only takes the first. enable_web_chat_single_call_hint
    in AgentLoop warns the model once per task when this happens.

    Emit real tool_calls fields. Ever.

    Stream tool calls separately from prose.

5. What changed this round
5.1 Request logging (bridge.py)

Every send now writes two things:

    bridge_logs/index.jsonl — one JSON line per attempt. Fields:
    ts, attempt, prompt_chars, prompt_tokens_est, messages_in,
    new_chat_fired, was_full_resend, prompt_capped, status,
    reply_chars, rate_limited, elapsed_ms.

    bridge_logs/sse/<id>.sse — full prompt, raw SSE body, parsed
    reply. Only written when SAVE_RAW_SSE = True.

This is the single most valuable diagnostic. Grep for "prompt_capped": true to see when the budget drop fired. Grep for "rate_limited": true
to see when DeepSeek throttled. Grep for "new_chat_fired": true to see
when the bridge did a full resend.
5.2 Message-size budget (bridge.py)

Two new constants:
python

MAX_PROMPT_CHARS = 80_000              # hard ceiling on prompt length
TOOL_RESULT_BRIDGE_CAP = 20_000        # hard ceiling on any one tool result

When the full-resend path fires with a conversation that would exceed
MAX_PROMPT_CHARS, build_prompt_under_budget drops messages from the
middle — keeps the first user message (the original task) and the
last N messages, inserts a system marker where the drop happened. Never
truncates mid-message (a half-rendered JSON object confuses the model
more than a missing chunk of history).

Why 80K: Playwright types one CDP event per character. 80K chars ≈ 10s
of typing. 200K chars ≈ 25s, before the model even starts generating.
DeepSeek's client-side cap is 2.6M chars — far above both the browser's
typing budget and the model's useful context.
5.3 Tool-result cap (bridge.py + ModelProfile.gd)

Two places:

    _cap_tool_result in the bridge, applied to any TOOL role message
    before rendering. Protects against session-resumption loading old
    conversations saved before AgentLoop's cap existed.

    WEB_CHAT.max_tool_result_chars lowered from 48_000 to 12_000 in
    ModelProfile.gd. Makes Godot do the right thing proactively, so the
    bridge-side cap rarely needs to fire.

5.4 WEB_CHAT tier (ModelProfile.gd)

A new tier distinct from the size tiers. It marks a large model reached
through a non-native endpoint. Inherits STANDARD's no-hand-holding
defaults, but:

    Enables synthetic tool-call recovery at a high cap (64)

    Injects SYSTEM_PROMPT_WEB_CHAT_PROTOCOL into the system prompt

    Leaves small-model nudges off (the model is smart enough to read a
    spec and follow it)

    Uses max_tool_result_chars = 12_000 and
    large_file_line_threshold = 600

ModelProfile.resolve_tier_from_model_name catches "deepseek-web",
"deepseek_web", "web-chat", and "web_chat" before the
parameter-count regex, so leaving the tier on "Auto" and naming the
model anything with deepseek-web in it resolves to WEB_CHAT.
6. The protocol mismatch — what to do about it

The current protocol (bare JSON) fights DeepSeek's training. Two
alternatives worth considering, in order of how much I'd trust them:
6.1 Tagged line format
text

TOOL: read_file
ARGS: {"path": "res://scripts/planet.gd"}

Two lines, TOOL: discriminator, ARGS: payload. Parsing is a regex,
not a brace-balancer. Why this beats bare JSON: DeepSeek will happily
write Let me read the file. {...} because writing JSON inline is
natural. It will not write Let me read the file. TOOL: read_file
because TOOL: is not a natural prose token. The discriminator does the
work that ten lines of "no prose before the JSON" in a system prompt
can't.
6.2 XML-ish tags

<tool_call>{"name": "read_file", "arguments": {...}}</tool_call>.
More distinguishable than bare braces. Downside: DeepSeek sometimes
emits ... for its own reasoning, so you'd have to strip those first
(which the parser already does).
6.3 Batch tool calls

Right now the recovery takes only the first JSON object per reply and
discards the rest. DeepSeek naturally wants to say "I'll search AND
look." Let it: parse all tool calls per reply, execute in sequence,
feed all results back in one message. Worth 2–3× throughput on a
typical task.

The meta-lesson: don't try to make DeepSeek behave like
Claude-with-tools. Make the protocol fit DeepSeek's existing behavior.
Every "nudge" and "recovery" is a symptom of fighting the wrong shape.
7. Failure modes and their fixes
7.1 Rate limiting

Symptom: DeepSeek replies with "Messages too frequent. Try again later." in the SSE body. Godot sees a normal assistant reply containing
that text and the agent gets confused.

Fix in place: _send_with_rate_limit_recovery in the bridge detects
the pattern (HTTP 429, 5xx, or the marker text in body/reply), waits a
cooldown (30s → 60s → 120s, capped at 240s), and retries internally up
to 3 times. If retries exhaust, returns a real HTTP 429 to Godot, where
LLMClient.gd's own backoff takes over.

Prevention: MIN_SEND_GAP_SECS = 4.0 enforces a floor between
sends. If you still see rate limits, raise to 8 or 12.
7.2 Empty response

Symptom: Model returned an empty response (finish_reason=stop) in
the Godot error log.

Cause: Rare — usually a DeepSeek UI hiccup where the SSE stream
closed without a status event. AgentLoop retries once via
MAX_EMPTY_RETRIES.
7.3 Tool call never executes

Symptom: Agent's reply looks like a tool call but no [Tool]
follows. Turn ends. Task stops.

Cause: One of the three failure shapes in §4.2 that recovery didn't
catch.

Fix: Check bridge_logs/sse/ for the raw SSE of that turn. Look at
the parsed reply. If it contains a JSON object the recovery should
have caught, that's a bug in _extract_fake_tool_call. If it contains
something else entirely (prose only, or a truncated fragment shape we
haven't seen), we need a new recovery pattern.
7.4 Full resend every turn

Symptom: Every request has "was_full_resend": true in the log.

Cause: Godot's ContextManager compaction is dropping messages
that the bridge remembers. After compaction, the incoming history no
longer starts with what the bridge's _known_messages has, so
is_prefix fails.

Fix: This is expected behavior after compaction. The message-size
budget (§5.2) makes it cheap. If it happens every turn with no
compaction, investigate why _known_messages isn't matching —
likely a message-shape difference (e.g. Godot added tool_calls where
the bridge remembers just content).
7.5 Reasoning text in the reply

Symptom: Assistant replies contain the model's internal
reasoning as well as its actual answer.

Cause: Pre-fix SSE parser accumulated both THINK and RESPONSE
fragments.

Fix in place: extract_reply_text tracks current_fragment_type
and only accumulates when it's exactly "RESPONSE".
7.6 Model stops mid-task

Symptom: Agent produces a normal text reply when the task clearly
isn't done.

Cause: Usually one of:

	Model emitted empty response (rare)

	Model gave up (nudged by enable_gave_up_escalation — off for WEB_CHAT)

	Model thought it was done

Fix: Look at the last few entries in bridge_logs/index.jsonl. If
reply_chars is small, the model probably gave up. If it's normal-sized
but the task isn't done, the reply text tells you why.

9. Debugging workflows
9.1 "The agent stopped mid-task"

    Open bridge_logs/index.jsonl, find the last few entries.

    Check elapsed_ms — was there a rate-limit cooldown?

    Check reply_chars — is the reply unreasonably short?

    Open the corresponding sse/<id>.sse file.

    Look at === PARSED REPLY === at the bottom. Does it contain a JSON
    object the recovery should have caught?

    If yes → bug in _extract_fake_tool_call.

	If no → the model didn't write a tool call. Check the raw SSE's last
    few data: lines to see what it did write.

9.2 "It's slow"

    Grep index.jsonl for high elapsed_ms.

    For each slow request, check:

        prompt_chars — is the prompt huge? (full resend territory)

        rate_limited — did DeepSeek throttle?

    If prompt_chars > 40_000: the full resend is expensive.

    If rate_limited: true frequently: raise MIN_SEND_GAP_SECS.

9.3 "It forgot what we were doing"

	Grep index.jsonl for "new_chat_fired": true around the failure.

    Check messages_in on that request — how many messages did Godot
    send?

    If it's small (< 5), Godot compacted. The model lost context.

    The fix is a state-handoff design (see §10.4), not more prompt
    engineering.

9.4 "The reply contains gibberish"

    Open the SSE file.

	Look for the response shell — search for "fragments".

	Check each fragment's "type". The parser should only accumulate
	"RESPONSE" fragments. If you see other types being accumulated,
    that's a parser bug.

    Check for search citations — they arrive as references arrays on
    fragments. Currently not filtered.

10. What's still on the table

Ordered by impact-per-hour-of-work.
10.1 Switch to a tagged protocol (§6.1)

Time: half a day. Impact: eliminates the "prose prefix" and
"truncated JSON" failure classes entirely. The current system recovers
from them, but every recovery costs a round trip.
10.2 Batch tool calls (§6.3)

Time: a few hours. Impact: 2–3× throughput on typical tasks.
Parse all tool calls per reply, execute in sequence, feed all results
back in one message.
10.3 Stream to Godot

Time: 1–2 days, both sides. Impact: changes the UX from "30s of
nothing then a reply" to "watch it happen." Makes timeouts detectable
mid-stream, lets partial replies be recovered.

Requires:

    LLMClient.gd: add stream: true support (parse OpenAI SSE chunks)

    bridge.py: translate DeepSeek SSE to OpenAI SSE chunks

10.4 State handoff instead of full transcript

Time: 1–2 days. Impact: makes full resends cheap. Currently the
budget drop handles this by cutting history; a proper handoff would
summarize it. Design:

    Keep the original task

    Last 4–6 messages verbatim

    One-line summary of every action taken (write/edit/check calls,
    pulled from the conversation)

    PlanStore's current state

8–15KB instead of 300KB. Faster to type, and the model gets a cleaner
starting point anyway.
10.5 Feed prior-turn THINK text forward

Time: a few hours. Impact: better multi-turn coherence. The
model has reasoned on the previous turn; feeding that reasoning back
as a system message shortens the next turn's reasoning and makes the
agent feel more continuous.
10.6 Filter search citations

Time: a couple of hours once we capture a search-triggered reply.
Impact: if search is what's polluting replies, this makes it go
away.
10.7 Prefer a native API

Time: zero — just change the endpoint.

If the DeepSeek account has any budget, api.deepseek.com/v1/chat/ completions natively supports tool calling, streaming, and structured
output. The entire bridge, the entire recovery path, the entire
rate-limit workaround, and the entire WEB_CHAT tier become
unnecessary. Cost is roughly $0.14 per million input tokens — a full
agent task is fractions of a cent.

Same is true of Groq (already in Settings — native tool calling,
generous free tier) and Ollama (native, local, no rate limits).

12. Rules for whoever touches this next

    Never make the bridge a tool-calling API. It never was; keep it
    that way. Recovery lives on the Godot side, where it can be disabled
    per tier.

    Log everything. Every new failure mode should have a
    corresponding field in index.jsonl before it becomes a nudge.
    Symptoms without metrics become guesses.

    Never truncate mid-message. A half-JSON object is worse than a
    missing one. Drop whole messages.

    Don't fight the model's prose instinct. The current protocol
    does, and it costs us recoveries on every turn. A better protocol
    (tagged lines) is on the table (§6.1).

    Test the recovery path before adding a new nudge. If
    _recover_truncated_tool_call already handles a shape, don't add a
    system message about it — the recovery is the fix.

    Check index.jsonl before guessing. The metrics file is the
    first thing to look at when something breaks.

    Keep WEB_CHAT free of small-model accommodations. No syntax
    cheatsheet, no act-don't-ask, no no-read nudge. It has its own
    protocol section and that's the only hand-holding it gets.

13. Known-good state as of this handoff

	Simple tasks ("read this file", "check this script") — work

    Medium tasks (5–10 tool calls) — work with occasional recovery

    Long tasks (15+ calls) — work but slow; expect one or two full
    resends due to compaction

    Rate limiting — recovered internally; rarely visible to Godot

    Reasoning leakage — fixed via extract_reply_text

    Tool call execution — relies on synthetic recovery; works when the
    model emits JSON, fails when it doesn't

What to fix next: look at index.jsonl after a real task. Whatever
metric is most anomalous tells you what to work on.
