## 2. What was built this session
 
### 2.1 `TscnParser.gd` (new)
 
A lightweight, best-effort `.tscn`/`.tres` text parser. Not a resource
loader — doesn't resolve UIDs, doesn't touch binary data, doesn't validate
correctness. It exists purely so other tools can turn raw `.tscn` syntax
into a node tree / ext_resource list instead of the model reading 40+
lines of `[node name="X" ...]` blocks by eye.
 
Parses:
- `[gd_scene]` / `[gd_resource]` header → format, load_steps
- `[ext_resource ...]` → id, type, path, uid
- `[sub_resource ...]` → id, type
- `[node ...]` → name, type, parent path, instanced-scene id, attached
  script id, and every `key = value` property line under it
 
`render_tree(scene)` renders the parsed node list as an indented outline
(depth derived from the `parent=` attribute string, not a real tree walk —
good enough for a readable summary, not authoritative on a scene with
unusual node declaration order).
 
### 2.2 Scene inspection tools (new, optional — handoff_file §5.2)
 
Four tools, all `ProjectPathTool` subclasses, `READ_PROJECT` permission,
built on `TscnParser`:
 
| Tool | Does |
|---|---|
| `inspect_scene` | Parses one `.tscn`, returns the node tree + ext_resource list |
| `find_node` | Finds node(s) by name/type substring, reports parent path |
| `get_node_property` | Reads one property's raw value for a named node, or reports it's not overridden in the scene file |
| `find_scene_users` | Finds every `.tscn` that instances a given scene and every `.gd` that preloads/loads it |
 
All four are registered/unregistered together under one Settings checkbox
("Scene tools").
 
### 2.3 `run_scenario` (new, optional — handoff_file §5.3)
 
The harness's first tool that lets the model **observe** behavior instead
of only reasoning about source. `GodotTool` subclass, `RUN_GODOT`
permission.
 
How it works:
1. Agent supplies `setup` — GDScript source for a `Node` script.
2. Tool writes it to `res://.agent_scenarios/<name>.gd`.
3. Tool generates a wrapper `res://.agent_scenarios/<name>.tscn`:
   a `ScenarioRoot` (Node, the scenario script) with the project's own
   `run/main_scene` instanced as a sibling child named `World`. This boots
   through a normal scene, not `--script` — autoloads and the project's
   real lifecycle stay intact, which `--script` would skip entirely.
4. Runs `godot --headless --path <project> <wrapper>.tscn`, capped at
   `duration` seconds (default 30, hard cap 120) plus an 8s slack window
   for process start/stop before it's killed as hung.
5. Scans stdout for the first line starting with `PASS:` or `FAIL:` and
   reports that as the verdict.
 
Two modes via the same `name` argument: `setup` non-empty writes/overwrites
and runs; `setup` empty re-runs the existing scenario unchanged — the
cheap regression-check path, since nothing has to be re-authored.
 
**No-fake-success guard (project rule #4):** a `PASS:` line is not trusted
if the same run also logged a real Godot `ERROR:`/`SCRIPT ERROR:` line —
that overrides to FAIL regardless of what the scenario printed. A timeout
is also reported as FAIL, not INCONCLUSIVE, since a scenario that never
reaches `get_tree().quit()` is a hang, not an ambiguous result.
 
`.agent_scenarios/` is a dot-directory, so it's already invisible to
`ProjectScanner`, `find_files`, `search_text`, and `check_project` — same
treatment as `.git`/`.godot` — meaning scenario test files never pollute
the project file listing or get flagged as things to "fix."
 
### 2.4 `MainWindow.gd` — wiring
 
- `OPTIONAL_TOOL_NAMES` extended with the 5 new tool names.
- `_setup_agent()` instantiates all 5 into `_optional_tools`. No special
  wiring code needed beyond instantiation — the existing generic loop in
  `_apply_tool_registration()` already type-checks for `GodotTool` (wires
  `process_manager`/`godot_executable` for `run_scenario`) and sets
  `project_root` on every registered tool regardless of type (covers the
  four `ProjectPathTool` scene tools). This is why the diff here is small.
- Two new system-prompt sections, each gated on whether their tool is
  actually registered (same pattern as `SYSTEM_PROMPT_PLAN_TOOLS`):
  `SYSTEM_PROMPT_SCENE_TOOLS` (gated on `inspect_scene`) and
  `SYSTEM_PROMPT_RUN_SCENARIO` (gated on `run_scenario`).
 
### 2.5 `SettingsDialog.gd` — new checkboxes
 
Two new checkboxes in the Tools section:
- **"Scene tools"** — toggles all four scene tools together.
- **"run_scenario"** — toggled separately, since it spawns a real Godot
  process per call and costs more than a read-only scene parse.
 
Both follow the existing disabled-tools persistence pattern
(`AppSettings.disabled_tools`), nothing new in `AppSettings.gd` itself.

## 4. Not yet verified
 
Same caveat as the prior handoff for the tagged protocol work: none of
this has run against a real Godot 4.7.2 project yet.
 
- `TscnParser`'s header/attribute regexes match documented `.tscn`
  format-3 syntax, but haven't been run against an actual scene file from
  any of the five active projects. The survival game's building-socket
  scenes (multi-floor, several `Area3D` snap points) or the voxel
  engine's chunk scenes are good first real-world tests — more nodes and
  odder ordering than a trivial scene would exercise `render_tree`'s
  depth logic properly.
- `run_scenario`'s wrapper `.tscn` (fixed `ExtResource` ids `"1"`/`"2"`)
  hasn't been loaded by a real Godot binary. Should load fine per format-3
  rules, but "should" isn't "verified."
- `find_scene_users`' `.gd`-side check (line must contain `preload(` or
  `load(`) is a simple substring test — it will miss a reference built up
  across multiple lines (e.g. a path concatenated into a variable before
  `load()` is called on it). Acceptable for a best-effort tool per its
  own framing, but worth knowing if a real search comes back empty when
  you expected a hit.

## 5. Roadmap — tools discussed for a future round
 
Not started. Ordered by effort-to-value, grounded in the actual projects
(survival game's RPC/self-RPC history, AnimationTree/combo-chain work,
shader-heavy day/night and path-texture systems, five simultaneous WIP
projects accumulating dead assets).
 
### 5.1 Cheap wins (small, self-contained, same `Tool` pattern as everything above)
 
- **`list_autoloads`** — reads `project.godot`'s `[autoload]` section
  (logic already exists in `GodotTool._load_autoload_names()` for the
  false-positive filter; this just exposes it as a callable tool)
  directly, name → path, in one call. Saves a `find_files` + `read_file`
  round trip every time the model needs to know what singletons exist.
- **`find_rpc_calls`** — `search_text`-style tool that specifically greps
  for `@rpc` annotations and `rpc(...)`/`rpc_id(...)` call sites and
  reports them together (declaration → every caller). Direct answer to
  the survival game's recurring "host calling `rpc_id(1,...)` on itself"
  bug class — right now catching that requires two separate manual
  searches merged by eye.
- **`find_signal_wiring`** — companion to `find_references`: for a given
  signal name, reports every `.connect(...)` and every `.emit()`/direct
  call site together. The codebase leans heavily on signals
  (`plan_changed`, animation transitions, UI updates); this is the
  find_symbol/find_references split applied to signals instead of
  declarations.
 
**Scope:** each is a half-day, independent, no dependencies between them.
 
### 5.2 Medium effort, high value
 
- **Godot API/docs lookup tool** — parses the local Godot install's
  bundled `doc/classes/*.xml` (every Godot build ships these) and returns
  a class's methods/signals/properties on request. Biggest lever against
  hallucinated API calls — wrong signal names, nonexistent methods on
  `CharacterBody3D`, etc. — which gets more likely as tasks touch
  `AnimationTree` state machines or `MultiplayerSynchronizer` config the
  model has seen less of in training.
- **`inspect_animation_tree`** — `TscnParser`-pattern reader specifically
  for `AnimationNodeStateMachine` / `AnimationNodeBlendSpace2D` resources:
  lists states, transitions, and blend points as an outline instead of
  raw resource syntax. Directly targets the BlendSpace2D + combo-chain +
  roll/lock-on debugging work already logged against the survival game.
- **`find_unused_resources`** — walks every `.tscn`/`.gd` for
  `preload`/`load`/`ext_resource` references (same walker shape as
  `find_scene_users`, run in reverse), reports project files with zero
  incoming references. With five active projects, dead scenes/scripts
  accumulate — this is a direct extension of `find_scene_users`' logic.
- **`run_scenario` profiler hook** — optional follow-up to what's already
  built: let a scenario print `Performance.get_monitor(...)` values
  (frame time, node count, physics time) and have the tool surface them
  alongside the PASS/FAIL verdict. Turns "did this change regress frame
  time" from a manual question into something `run_scenario` answers
  directly — relevant for voxel chunk generation and MOBA bot pathing.
 
**Scope:** roughly a day each; independent of one another.
 
### 5.3 Bigger, architectural (deferred in the prior handoff too)
 
- **Git integration** (`git_status`/`git_diff`/`git_checkpoint`/
  `git_revert_checkpoint`) — replaces the internal checkpoint stash with
  something inspectable outside the agent, for whichever of the five
  projects has a repo. Git should stay optional — the agent must keep
  working without it via the existing `CheckpointManager` path.
- **Godot Editor bridge (EditorPlugin)** — lets the agent query the
  *live* open editor (selected node, open scene, in-editor errors)
  instead of only static files. Highest payoff specifically for
  AnimationTree/combo-chain debugging, where "what does the state
  machine look like right now in the editor" is the actual question.
- **Read-only research subagent** — bounds a sub-task ("investigate how
  the city-builder calculates path cost") to a subagent that cannot
  write, so exploration can't accidentally touch files mid-investigation.
  Worth building once a task routinely spans multiple systems (e.g.
  "why does taming interact badly with the day/night cycle").
 
**Scope:** 1–2 days each; each is a standalone vertical slice, no
particular order required between them.

## 6. Design rules that still apply
 
Restated from `projectstructure.txt` / `handoff_file`, because every item
in §5 above has to respect them:
 
- The LLM is the reasoner; the Godot app is the harness — no task-specific
  logic belongs in `AgentLoop`.
- Every new tool declares `required_permission`; `PermissionManager`
  decides, never the model.
- Sandbox enforcement is code (`ProjectPathTool.resolve_path`), never
  just prompting.
- No fake success — a verdict is never trusted over contradicting
  evidence in the same run (see `run_scenario`'s error-override rule,
  §2.3 above).
- Bounded tool output — every new search/list tool needs a result cap
  and truncation-safe formatting, same as `find_files`/`search_text`.
- Every new tool schema is a fixed token cost paid on every single API
  call, for every tier, even ones that never use it. New tools default to
  the optional-tools list (like the 5 built this round) unless there's a
  specific reason to make one always-on.
- Hints/errors derive from structured data, never a raw-text guess
  dressed up as a fact.
- Clean-room implementation only.
 
---
 
## 7. Recommended order for the roadmap in §5
 
1. **§5.1 items** — cheapest, independent, and `find_rpc_calls` in
   particular closes a bug class that's already bitten the survival game
   more than once.
2. **Godot API/docs lookup** — highest generic leverage of the §5.2 items;
   reduces hallucination risk across every project, not just one.
3. **`inspect_animation_tree`** — highest project-specific leverage,
   given how much AnimationTree/combo work is already logged.
4. **`find_unused_resources`** — pure cleanup value, no urgency.
5. **`run_scenario` profiler hook** — natural follow-up once `run_scenario`
   itself has been run against a real project and confirmed working.
6. **§5.3 items** — defer until a concrete task keeps being harder than
   it should be without them; each is a bigger lift than anything above.
